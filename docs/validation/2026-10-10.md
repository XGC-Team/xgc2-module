# Validation record, 2026-10-10

What was run for xgc2-module 0.2.0 (module ABI 2.0), with the commands, and what came out. Revision under test:
2cc45c3 on branch `issue-226-xgc2-module`, including per-instance worker affinity. The package and original XRPC
path-patch results below are from before affinity.

## Machine and toolchains

Ubuntu 20.04 x86_64 virtual machine, 8 vCPUs (Intel Xeon, 2.4 GHz), kernel 6.12.94, **shared with other build jobs**
(load average between 0.4 and 26 during this work), no root, no Docker. rustc 1.93.0 (stable) and 1.85.0 (the MSRV),
gcc 9.4 and, through the Bionic sysroot, gcc 7.5 with glibc 2.27, cmake 3.16, Python 3.8.

Stable 1.93 debug, release, MSRV 1.85, and Bionic each pass **120 tests, 0 failures** (57 unit, 63 integration).
Formatting, Clippy and rustdoc are clean; the 30 s release hot-plug soak passes. Logs are in
`target/affinity-validation/` in the worktree.

Two test setup issues were corrected during affinity validation. The event-backlog test measured the old consumer's
read count before replacement creation. Sticky creation shares that consumer's worker, so the consumer can drain
the backlog before the control thread reaches quiescence. That test now explicitly retains its original `any`
affinity for producer and consumer; sticky replacements are covered by the new OS-thread probe tests and the
existing hot-plug chain tests. The probe's trace directory now outlives fixture shutdown, so destruction can record
its thread before temporary files are removed.

The SDK consumer and Debian package checks recorded below were run before affinity; they were not rebuilt for this
scheduler change. The public header changes only comments, and `abi_layout` still checks the C/Rust ABI on both
native and Bionic builds.

Flake hunting before the affinity follow-up: the whole suite 10 times in a row at a machine load average between 9 and 18 (other
jobs), then 4 times with 8 busy loops competing for the 8 vCPUs on top of that, and the soak in release mode for
2 x 30 s (about 15,700 random hot-plug operations each). One of the first ten runs failed: the steady-clock timer unit
test asserted a mean expiration interval, which an overloaded machine stretches by merging periods. It now asserts only
what holds on any machine (no expiration comes early, the timer stops when disarmed), and a new test on the external
clock, where the test decides when each expiration is noticed, checks that late expirations do not shift the deadlines
after them (it fails against a timer that counts the next period from the moment it fired). After the fix all 14 runs
passed. The host itself had no failure; an earlier round of the same hunt found a test that started the clock source of
a manifest before the timer it drives ("Start the clock source last in the manifest clock test").

* The binary needs `GLIBC_2.25` at most (`objdump -T`); its interpreter is the system loader, and
  `LD_TRACE_LOADED_OBJECTS=1 ld-2.27.so --library-path ... xgc2-module-host` resolves libc, libdl, libpthread and
  libgcc_s inside the sysroot.
* All 120 tests pass with every test process (and the host binary of the command line tests) running on the glibc 2.27
  loader and libc of the sysroot.
* The same release binary is what the Debian packages ship, so one build serves 18.04, 20.04 and 24.04.

## Benchmark

Revision `2cc45c3`, benchmark binary SHA256
`e0ceb434219f3b11f6108d81f119faa1ff09271170076d5d4a0ae269c51259ec`.
The updated `handoff` benchmark measures both sticky (the default) and any affinity in the same executable,
with 4, 2 and 1 worker(s). Each chain uses a producer at 500 Hz, an input-driven pass-through stage and an
input-driven sink. Sink, stage and producer are added in that order: sticky home slots are 0, 1, 2 with four workers,
0, 1, 0 with two workers, and all 0 with one worker. Any affinity uses free dispatch and run-next.

Each module stamps its output with `now_ns()` immediately before `write_commit`; the next module measures
`step_ctx.now_ns - view.stamp_ns`. End-to-end time uses the original producer stamp carried in the payload.
The first 500 samples are dropped, and every chain/fan-out measurement runs 15 s after a 1 s warm-up. Process CPU
comes from `getrusage`; thread wake-ups are voluntary context switches from `/proc/self/task`. Modules do not
report per step. The host's histogram measures the oldest unprocessed commit, while modules measure the latest
sample they read: coalescing can make the host's histogram larger under contention (bucket error at most 12.5%).

With the stable environment from the tests section:

```bash
XGC2_BENCH_SECONDS=15 XGC2_BENCH_OUT="$PWD/target/affinity-validation/handoff.md" cargo bench -j 2 --locked --offline --bench handoff
XGC2_BENCH_SECONDS=15 XGC2_BENCH_OUT="$PWD/target/affinity-validation/handoff-repeat.md" cargo bench -j 2 --locked --offline --bench handoff
```

Both complete benchmark runs passed. No host build or test job of this package ran during either measurement.
The shared VM remained active: the first run started at load average 9.67 / 10.05 / 7.83; the repeat started at
3.10 / 6.90 / 7.06. The repeat is tabulated below. Neither run was CPU-pinned or isolated; the sample counts,
preemptions, missed periods and overruns show scheduling noise. These measurements are not worst-case guarantees.

### Affinity cost

* With four workers, sticky requires a producer wake-up plus one wake-up at each hop. The repeat measured 23.5 / 270.5 us
  end to end at p50 / p99, 1.73% of one core and 2,097 thread wake-ups/s. Any ran the chain back to back on a worker:
  3.6 / 6.7 us, 1.15% of one core and 1,094 wake-ups/s. The first run's different latency tails show why these values
  must be read with the shared-machine conditions above, rather than as fixed scheduler limits.
* One worker co-locates all three sticky instances, enabling run-next: p50 / p99 3.0 / 5.2 us for sticky and
  2.8 / 4.8 us for any in the repeat. Both cost about 1.1% of one core and about 1,100 wake-ups/s when timers keep up.
* Sticky supports thread-affine module libraries and preserves worker cache locality. It also makes an instance
  wait for co-located calls; a hang delays that lane until its replacement worker starts in the same slot. Any can
  use other workers and the watchdog can steal its pending run-next tasks.
* The idle host costs about 0.1% of one core and 100 wake-ups/s (the watchdog tick). Fan-out uses any affinity in
  these measurements. Tails and missed periods vary with other jobs on this VM; no real-time policy is configured.

* Sanitizers, Miri and loom (not installed offline), hangs inside `create`/`start`/`stop` (same watchdog, 5 s floor, no
